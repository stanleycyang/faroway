# Trip recovery rollout and rollback

This is a proposed, unexecuted production change for the recovery draft PR. The production baseline supplied for review is `4f68fe54`. Apply only after approval of the exact release commit and SQL files. Keep provider activation, payments, affiliate credentials and bookings outside this rollout.

Administrative SQL and existing SECURITY DEFINER maintenance functions can still write as privileged roles; inspect the deployed function definitions and job inventory, not only table RLS. In particular the old timeout cleanup must be replaced before enabling retries/reconciliation. Repository inspection does not prove the deployed schema has no drift or additional jobs.

## Preconditions

- Exact release commit CI passes quality, unit tests, disposable PostgreSQL tests, full browser/compiled Workflow tests, and the normal production build. Keep the PR draft until review finishes.
- Rehearse the sequence on an isolated staging database using the actual deployed schema definitions. Current PostgreSQL tests use a representative schema, not a production clone. Confirm table types, FKs, trigger ordering, grants, function owners, search writers, cron jobs and the migration ledger. Inspect definitions/counts without exporting traveler data or secrets.
- Confirm an available database backup/PITR recovery point and operator access. DDL should use a short lock timeout (for example 5 seconds) and bounded statement timeout (for example 60 seconds). A lock timeout aborts the phase; do not retry indefinitely under traffic.
- Identify the exact old production deployment and every older deployment that can receive user traffic or resume durable jobs. Obtain the workflow backend's run/queue inventory, including pending, running and retrying work. Database status or elapsed time alone is not proof of termination. Old unverified bindings need independently confirmed backend identity before any manual repair; that repair requires a separate reviewed operation.
- Prepare the new release with `FAROWAY_PLANNING_PAUSED=true`. This flag blocks new POST planning through canonical trip generation, search/start, and streaming/non-streaming itinerary APIs; the compatibility itinerary/generate route delegates to those handlers and the legacy workflow endpoint returns 410. Reconciliation also fails closed while paused. Saved trips, reads and sharing remain available. Existing dispatched workflows are not canceled by the flag.

## Ordered rollout

1. Apply only migrations **001000, 003000 and 004000** above, each in a controlled transaction with lock/statement timeouts. Verify function grants, verified-column defaults, both search-trigger rejection and permitted service-role writes, and the non-mutating timeout cleanup in staging first. Record the selected versions in the approved migration ledger. **Do not run an indiscriminate migration push:** numeric order would install the trip trigger too early.
2. Cut over to the reviewed application release with planning paused. Confirm the production alias resolves to that exact deployment. Verify authenticated share/revoke handlers are the new service-role implementation and saved-trip reads work. No provider keys or commercial feature gates change.
3. Drain old HTTP requests and old durable runs. Require positive evidence that old deployments cannot accept new user traffic and have no pending/running/retrying workflows or in-flight writes. Account for direct old deployment URLs, retries and scheduled invocations. If that cannot be established, remain paused and withhold the trip trigger/unpause approval. Waiting a fixed number of minutes is insufficient for durable runs. New code cannot retroactively fence old workflow code.
4. Apply **002000** (trip lifecycle protection) in a controlled transaction only after the new share handlers are serving and old requests have drained. Verify its definition and grants/roles against the reviewed SQL. Confirm no old share handler or incompatible direct client write remains in supported traffic.
5. Review staging results and production read-only health/aggregate observations. Any production canary that creates a trip, changes sharing or starts a workflow is a separate explicit approval item; do not silently treat it as a read-only check. Only after all acceptance criteria pass, approve a new release configuration with planning unpaused. Do not automatically retry unidentified starts.

If any prerequisite fails, stop at that phase and retain the pause. The planned order is intentionally different from filename order. Do not edit the migration ledger to conceal an unexecuted or failed migration.

## Rollback and limits

- Before cutover, the added RPC can remain unused. If search-write compatibility fails, pause new planning before removing the search trigger. Do not enable reconciliation with unprotected bindings. The verification column may remain; do not drop it while new code or queued new workflows reference it.
- Prefer rolling forward or reverting to a tested compatibility release that retains service-role share handlers, attempt fences and the pause. Keep all protective SQL in place.
- A direct rollback to `4f68fe54` **with the trip trigger still installed breaks share/revoke**. If that older build must be restored, first keep new planning paused, drain new workflow/HTTP writers, and obtain explicit approval to remove the trip trigger. This reopens the original authenticated lifecycle-write vulnerability. Deploy the older build only after the incompatible trigger is removed. Old production does not honor the new pause flag, so an independently reviewed ingress maintenance control is required before that rollback; without one, do not perform it.
- Keep `apply_trip_generation_update` available while any new-version durable run can resume, even if the application is rolled back. Dropping it can strand queued workflows. Keep the timeout cleanup replacement: restoring timeout-based failure can duplicate paid work and requires separate explicit risk approval.
- These migrations do not undo published itineraries, notifications or trip status changes already committed by the new application. Revoked public tokens must remain revoked. Never restore them as part of rollback. PITR is a separate destructive recovery operation with wider data loss implications, not the default rollback.
- No migration rollback should delete trips/searches or reset generating states by age. Unknown dispatch/run identities remain blocked pending positive evidence.

## Launch acceptance and subsequent scope

Recovery launch requires passing exact-commit CI, a successful staging rehearsal, reviewed real-schema compatibility, verified server-only run bindings, rejection of direct lifecycle mutations, no timeout-only retry release, one winning concurrent generation claim, stale-attempt rejection, successful interrupted-create/refresh recovery, explicit sharing consent/revocation, and verified old-workflow drain. Provider content/checkout gates remain off unless their independent approvals exist.

Next product slice: persist the complete trip brief (including traveler composition, interests, origin, budget and vibes); edit with a revision token; reject concurrent/stale saves and changes during generation at the database boundary; show when the displayed itinerary belongs to an older brief. Subsequent itinerary editing must use an immutable plan revision, explicit locked choices, constrained swaps, undo and confirmation before regeneration. No edit may silently change an already-purchased item or imply a live quote. The smallest commercial launch adds only approved hosted-provider handoff with explicit consent, durable handoff recovery and honest commission attribution, not a universal one-payment cart.
